## Décision

Deux nouvelles règles MC ajoutées au projet `MathCursor.Analyzers` :

### MC0009 — SuppressMessage sans Justification référençant un ADR

**Verrou anti-suppression silencieuse.** Toute `[SuppressMessage(...)]`
doit citer un ADR via `Justification` : soit le token `ADR` (case-
insensitive), soit un slug de décision projet
`YYYY-MM-DD-(Meta|Feat|Fix|Refactor|UX|Release|Test|Limit)`.

**Severity** : `warning` dès le départ — il n'y a aucune occurrence
existante à nettoyer (le repo n'utilise pas `SuppressMessage` à ce
jour). Promotion en `error` à terme.

**Cas dynamiques** : `Justification = SomeConstant` (variable / nameof)
n'est pas résolu statiquement → faux négatif assumé.

### MC0006 — Splice LaTeX sur texte rendu (anti-pattern racine)

**Capture l'anti-pattern du bug double-wrap résolu commit `9ab248b`
(2026-05-11)** : `topLatex.Substring(0, x) + altLatex + topLatex.Substring(y)`
opère sur le texte DÉJÀ rendu (avec wraps `\left(...\right)` posés par
le parser). Splicer une alt qui est elle-même la décoration courante
produit `\left(\left(AB\right)\right)` (parens), `\widehat{\widehat{ABC}}`
(angle), `\vec{\vec{AB}}` (vec).

**Détection** :
- `InvocationExpressionSyntax` sur `.Substring(...)`.
- Receveur typé `string` (via `SemanticModel`).
- Nom du receveur contient `topLatex` / `*top*+*latex*` / `*latex*` /
  `*rendered*` (case-insensitive).
- Le résultat est concaténé (`+`) à au moins une autre expression
  (= pattern splice, pas un Substring isolé qui peut être légitime).

**Severity** : `info` dans l'analyzer, promue à `warning` via
`.editorconfig`. **Non bloquante** dans `MathCursor.Core.csproj` via
`<WarningsNotAsErrors>...;MC0006</WarningsNotAsErrors>` tant que le
refacto vers source-mutation (axe A extensibilité) n'est pas fait.

**Hits actuels sur le repo** :
- `core-csharp/src/MathCursor.Core/ZoneResolver.cs:205` (le splice
  racine, attendu — sera refacto via SourceMutation à l'étape 3+
  extensibilité).
- `core-csharp/tests/MathCursor.Core.Tests/Lattice/AlternativeGeneratorTests.cs:182,184`
  (test qui SIMULE le splice pour valider — légitime, candidat à
  `SuppressMessage` avec ADR ciblé).

## Pourquoi

- **MC0001 (Phase 0+1) seul ne suffit pas.** L'utilisateur a explicité :
  "MC0001 c'était un exemple foireux que j'avais trouvé, mais y'en a
  plein". Le brief proposait MC0001-5 plus MC9999 (suppression sans
  ADR). On en ajoute 2 : MC0009 (= MC9999 renommé pour cohérence
  numérique) et MC0006 (custom, anti-pattern observé in vivo sur ce
  projet).

- **MC0006 est l'anti-pattern qu'on vient de débugger.** Le commit
  `9ab248b` du 11-05 a résolu un bug user-facing (`(AB) perp EF`
  → `\left(\left(AB\right)\right) \perp \left(EF\right)`) qui venait
  exactement de ce splice. La règle agit comme garde-fou pédagogique
  permanent : tout futur splice de LaTeX sera signalé, oblige une
  réflexion sur la nature de la mutation (source vs rendu).

- **MC0009 protège contre la dérive silencieuse.** Une `SuppressMessage`
  sans ADR est l'équivalent code d'un commit sans message — non
  traçable, dilue la rigueur des règles MC. Le verrou est rapide à
  implémenter et zéro coût car aucune `SuppressMessage` n'existe
  encore dans le repo.

## Tradeoff & alternatives écartées

- **MC0006 plus strict** (matcher exactement le pattern triple
  `var = var.Substring + alt + var.Substring`) : rejeté car implémentation
  complexe (comparaison de symboles de variables, parcours associatif
  des `+`). L'approche heuristique nom + concaténation suffit à attraper
  le cas réel (validé empiriquement par la détection de `ZoneResolver:205`).

- **MC0006 en `error` directement** : rejeté, casserait le build tant
  que `ZoneResolver:205` n'est pas refacto. `warning` + override
  `WarningsNotAsErrors` permet de voir les hits sans bloquer le travail
  courant.

- **MC0006 sur `.Replace(...)` aussi** (autre forme de splice) : reporté.
  La règle actuelle ne couvre que `.Substring` car c'est ce qu'on
  observe. Si un `.Replace` problématique apparaît, on étend.

- **MC9999 plutôt que MC0009** (numérotation alignée sur le brief) :
  rejeté pour la cohérence — les règles MC sont numérotées séquentiellement
  côté projet (MC0001, MC0002, MC0003... MC0009). MC9999 réservé pour
  des règles méta de l'analyzer lui-même.
